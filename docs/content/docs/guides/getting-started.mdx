title: Getting Started
description: Add Clifacet to your Cargo project, define a command core, and execute it across terminal modes.

Clifacet keeps one command core and runs it in three terminal modes: noninteractive
(flags in, output out), interactive (a questionnaire on a terminal), and a TUI (a
full-screen form). A run takes the lowest mode that can answer, unless a flag or the
application asks for more. The command never writes a stream and never reads a
terminal — that is what makes the same command reachable from all three, and testable
without any of them.

<Callout type="info">
Because the command core is decoupled from presentation, commands do not inspect terminal streams or format raw text. Input validation happens before execution, and output is structured data.
</Callout>

<Steps>
<Step>

## Add Dependencies

Configure your package manager to include `clifacet`. Clap is re-exported and routed automatically through `clifacet::clap`, so your application only requires one direct dependency:

<Tabs items={["Cargo.toml", "cargo add"]}>
  <Tab value="Cargo.toml">
    ```toml
    [dependencies]
    clifacet = { version = "0.8.0", features = ["tui", "interactive"] }
    ```
  </Tab>
  <Tab value="cargo add">
    ```sh
    cargo add clifacet --features tui,interactive
    ```
  </Tab>
</Tabs>

### Features

Every optional feature is off by default, and each one is a dependency boundary:

| Feature | Description | Dependencies |
| --- | --- | --- |
| *(default)* | Commands, companion derive, interaction policy, secrets, provenance | `thiserror`, `clifacet-macros` |
| `interactive` | Terminal dialogs powered by `inquire` | `inquire` |
| `tui` | Full-screen terminal forms powered by `ratatui` | `ratatui`, `crossterm` |
| `serde` | Serializes `Failure`, `FailureKind`, `Secret`, and `--json` mode | `serde`, `serde_json` |
| `schema` | Machine-readable CLI schema introspection | `serde`, `serde_json` |
| `skill` | Pluggable skill rendering for agent documentation | `serde`, `serde_json` |
| `skill-minijinja` | Built-in MiniJinja skill renderer for agent documentation | `minijinja`, `serde`, `serde_json` |
| `mcp` | Model Context Protocol stdio tool server | `serde`, `serde_json` |
| `completions` | Context-aware dynamic shell completions | `serde`, `serde_json` |
| `async` | Native async command execution, cancellation, and progress | *(none — std futures)* |
| `settings-toml` | Flat TOML configuration parser | `toml_edit` |
| `settings-figment` | Hierarchical configuration powered by Figment | `figment`, `serde`, `serde_json`, `toml_edit` |

</Step>

<Step>

### Declare the Controller and Commands

Clifacet's canonical authoring style uses declarative macros. An application controller declares CLI metadata with `#[clifacet::app]`, and commands are methods on the controller annotated with `#[clifacet::commands]`:

```rust
use clifacet::Failure;

/// An application controller declares its global surface and commands.
#[clifacet::app(name = "greet", about = "Say hello", commands)]
struct GreetApp {}

#[clifacet::commands]
impl GreetApp {
    /// The greeting command: parameters are arguments and flags.
    pub fn hello(
        &self,
        #[clifacet(long, short = 'n', help = "Who to greet", default_value = "world")]
        name: String,
        #[clifacet(long, help = "How many times", default_value_t = 1)]
        repeat: u8,
    ) -> Result<String, Failure> {
        Ok(format!("hello, {name} x{repeat}"))
    }
}
```

Method parameters become arguments and options with automatic help generation and type validation. Commands return structured data (`Result<T, Failure>`) rather than formatting or printing directly to terminal streams.

</Step>

<Step>

### Run the Command with App

The runner coordinates argument parsing, conversational prompts for missing values, command execution, and exit codes:

```rust
use clifacet::contract::ExitPolicy;
use clifacet::policy::{Capabilities, Mode, Policy};
use clifacet::Failure;

#[clifacet::app(name = "greet", about = "Say hello", commands)]
struct GreetApp {}

#[clifacet::commands]
impl GreetApp {
    pub fn hello(
        &self,
        #[clifacet(long, short = 'n', help = "Who to greet", default_value = "world")]
        name: String,
        #[clifacet(long, help = "How many times", default_value_t = 1)]
        repeat: u8,
    ) -> Result<String, Failure> {
        Ok(format!("hello, {name} x{repeat}"))
    }
}

// The binary's whole `main`:
fn main() -> std::process::ExitCode {
    clifacet::run_cli::<GreetApp>()
}

// In tests or headless pipelines, run without a process terminal:
let (mut out, mut err) = (Vec::new(), Vec::new());
let code = clifacet::App::<GreetApp>::for_cli()
    .policy(Policy::up_to(Mode::Interactive))
    .exit(ExitPolicy::standard())
    .run_with(
        ["greet", "hello", "--name", "ada"],
        Capabilities::headless(),
        || Box::new(clifacet::prompt::Terminal::new(std::io::empty(), std::io::sink())),
        &mut out,
        &mut err,
    );
assert_eq!((code, out.as_slice()), (0, b"hello, ada x1\n".as_slice()));
```

<Callout type="info">
Declarative controllers are the canonical authoring style in Clifacet. For specialized needs such as planned dry runs or custom bridge conversions, Clifacet also supports struct-based commands implementing the `Command` or `Planned` trait. See [The Companion Derive](derive.md) and [Command Core](../reference/command-core.md).
</Callout>

</Step>

## Runner Execution Lifecycle

The runner evaluates execution steps in a strict, predictable order:

| Step | Interruption Cause | Standard Exit Code |
| --- | --- | --- |
| `parse` | `--help` or `--version` requested on stdout | `0` |
| `parse` | Flag usage or grammar error on stderr | `2` |
| `settle mode` | Requested mode is forbidden by policy or unsupported by terminal | `2` |
| `ask` | User declined or aborted an interactive question (Ctrl+C) | `130` |
| `validate` | A field rule or bridge conversion fails | `2` |
| `run` / `preview` | Command execution failure | `1` (`2` for validation failure) |
| `write output` | Destination stream cannot be written | `1` |

## Advanced Customization

<Accordions>
<Accordion title="Customizing the Application Runner (App Builder)">

`clifacet::run::<Cli>()` defaults to `App::<Cli>::new().run()`. You can customize execution behavior using builder methods:

- `.policy(..)`: Configures the ceiling and default interaction level ([Modes Concept](../concepts/modes.md)).
- `.mode_from(..)`: Binds custom flags like `--interactive` or `--tui`.
- `.context(..)`: Injects dependency state (databases, HTTP clients, stores).
- `.render(..)`: Customizes output rendering.
- `.exit(..)`: Overrides standard exit codes.

</Accordion>

<Accordion title="Injecting Application Context Dependencies">

Commands declare user input, not application resources. Shared state (such as stores or database connections) is provided via `App::context`:

```rust
use clifacet::command::{Plan, PlannedWith};
use clifacet::prompt::Scripted;
use clifacet::{App, Failure, Globals};

#[clifacet::command(input = DoneInput)]
#[derive(Clone)]
#[command(name = "done")]
struct Done {
    #[arg(long)]
    task: String,

    #[command(flatten)]
    #[clifacet(skip)]
    globals: Globals,
}

struct DoneInput {
    task: String,
}

struct Store {
    open: Vec<String>,
}

#[clifacet::planned]
impl PlannedWith<Store> for Done {
    type Input = DoneInput;
    type Output = String;

    fn plan<'a>(&'a self, input: DoneInput, store: &'a Store) -> Result<Plan<'a, String>, Failure> {
        if !store.open.contains(&input.task) {
            return Err(Failure::validation(format!("there is no open task named {}", input.task)));
        }
        let step = format!("mark {} done", input.task);
        let task = input.task;
        Ok(Plan::new(move || Ok(format!("{task} is done"))).step(step))
    }
}

let store = Store { open: vec![String::from("CLI-47")] };
let app = App::<Done>::new().context(move || Ok::<_, std::io::Error>(Store {
    open: store.open.clone(),
}));
let (mut out, mut err) = (Vec::new(), Vec::new());
let code = app.run_with(
    ["done", "--task", "CLI-47", "--dry-run"],
    clifacet::policy::Capabilities::headless(),
    || Box::new(Scripted::new([])),
    &mut out,
    &mut err,
);
assert_eq!((code, out.as_slice()), (0, b"mark CLI-47 done\n".as_slice()), "{err:?}");
```

</Accordion>

<Accordion title="Settings from a file, under the flags">

### Settings from a file, under the flags

A flag is one place a value comes from. The other three, in the order they win, are the
environment, a settings file, and the built-in default. `App::settings` supplies the third,
and nothing else changes: the file's values become `clap` defaults, so the order is `clap`'s
own and each value is parsed by the same parser as the flag.

```rust ignore
use clifacet::settings::toml::Toml;

App::<Cli>::new()
    .settings("my-app", Toml)
    .run();
```
