---
title: Getting Started
description: Add Clifacet to your Cargo project, define a command core, and execute it across terminal modes.
---

Clifacet keeps one command core and runs it in three terminal modes: noninteractive
(flags in, output out), interactive (a questionnaire on a terminal), and a TUI (a
full-screen form). A run takes the lowest mode that can answer, unless a flag or the
application asks for more. The command never writes a stream and never reads a
terminal — that is what makes the same command reachable from all three, and testable
without any of them.

<Callout type="info">
Because the command core is decoupled from presentation, commands do not inspect terminal streams or format raw text. Input validation happens before execution, and output is structured data.
</Callout>

<Step>

## Add Dependencies

Configure your package manager to include `clifacet` and `clap`:

<Tabs items={["Cargo.toml", "Pixi"]}>
  <Tab value="Cargo.toml">
    ```toml
    [dependencies]
    clifacet = { version = "0.7.0", features = ["tui", "interactive"] }
    clap = "4.6.7"
    ```
  </Tab>
  <Tab value="Pixi">
    ```sh
    pixi add clifacet --channel conda-forge
    ```
  </Tab>
</Tabs>

### Features

Every feature is off by default, and each one is a dependency boundary:

| Feature | Description | Dependencies |
| --- | --- | --- |
| *(default)* | Commands, companion derive, interaction policy, secrets, provenance | `clap`, `thiserror`, `clifacet-macros` |
| `interactive` | Terminal dialogs powered by `inquire` | `inquire`, `crossterm` |
| `tui` | Full-screen terminal forms powered by `ratatui` | `ratatui`, `crossterm` |
| `serde` | Serializes `Failure`, `FailureKind`, and `Secret` | `serde` |
| `settings-figment` | Hierarchical configuration powered by Figment | `figment` |
| `settings-toml` | Flat TOML configuration parser | `toml_edit` |

</Step>

<Step>

### Write the Command Core

A `Command` is a value that takes validated input and returns data or a failure:

```rust
use clifacet::{Command, Failure};

struct Greet;

impl Command for Greet {
    type Input = String;
    type Output = String;

    fn execute(&self, input: Self::Input) -> Result<Self::Output, Failure> {
        Ok(format!("hello, {input}"))
    }
}

let greeting = Greet.execute("ada".to_owned()).expect("a greeting");
assert_eq!(greeting, "hello, ada");
```

`Input` is built *after* validation, so `execute` has nothing left to reject, and
`Output` is data rather than a message.

</Step>

<Step>

### Run the Command with App

Everything around the command — parsing, asking for what flags left out, validation,
and exit codes — is coordinated by the runner:

```rust
use clifacet::policy::Capabilities;
use clifacet::prompt::{Prompter, Scripted};
use clifacet::{App, Command, Failure, Globals};

#[clifacet::command(input = Greeting)]
#[derive(Clone)]
#[command(name = "greet", about = "Say hello")]
struct Greet {
    /// Who to greet.
    #[clifacet(long, ask = "Who should I greet?", fill = "world")]
    name: Option<String>,

    /// `--yes` and `--dry-run`, which every application gets.
    #[command(flatten)]
    #[clifacet(skip)]
    globals: Globals,
}

struct Greeting {
    name: String,
}

impl Command for Greet {
    type Input = Greeting;
    type Output = String;

    fn execute(&self, input: Greeting) -> Result<String, Failure> {
        Ok(format!("hello, {}", input.name))
    }
}

// The binary's whole `main`:
fn main() -> std::process::ExitCode {
    clifacet::run::<Greet>()
}

// `run_with` runs without a process terminal:
let (mut out, mut err) = (Vec::new(), Vec::new());
let code = App::<Greet>::new().run_with(
    ["greet", "--name", "ada"],
    Capabilities::headless(),
    || -> Box<dyn Prompter> { Box::new(Scripted::default()) },
    &mut out,
    &mut err,
);
assert_eq!((code, out.as_slice()), (0, b"hello, ada\n".as_slice()));
```

</Step>
</Steps>

## Runner Execution Lifecycle

The runner evaluates execution steps in a strict, predictable order:

| Step | Interruption Cause | Standard Exit Code |
| --- | --- | --- |
| `parse` | `--help` or `--version` requested on stdout | `0` |
| `parse` | Flag usage or grammar error on stderr | `2` |
| `settle mode` | Requested mode is forbidden by policy or unsupported by terminal | `2` |
| `ask` | User declined or aborted an interactive question (Ctrl+C) | `130` |
| `validate` | A field rule or bridge conversion fails | `2` |
| `run` / `preview` | Command execution failure | `1` (`2` for validation failure) |
| `write output` | Destination stream cannot be written | `1` |

## Advanced Customization

<Accordions>
<Accordion title="Customizing the Application Runner (App Builder)">

`clifacet::run::<Cli>()` defaults to `App::<Cli>::new().run()`. You can customize execution behavior using builder methods:

- `.policy(..)`: Configures the ceiling and default interaction level ([Modes Concept](../concepts/modes.md)).
- `.mode_from(..)`: Binds custom flags like `--interactive` or `--tui`.
- `.context(..)`: Injects dependency state (databases, HTTP clients, stores).
- `.render(..)`: Customizes output rendering.
- `.exit(..)`: Overrides standard exit codes.

</Accordion>

<Accordion title="Injecting Application Context Dependencies">

Commands declare user input, not application resources. Shared state (such as stores or database connections) is provided via `App::context`:

```rust
use clifacet::command::{Plan, PlannedWith};
use clifacet::prompt::Scripted;
use clifacet::{App, Failure, Globals};

#[clifacet::command(input = DoneInput)]
#[derive(Clone)]
#[command(name = "done")]
struct Done {
    #[arg(long)]
    task: String,

    #[command(flatten)]
    #[clifacet(skip)]
    globals: Globals,
}

struct DoneInput {
    task: String,
}

struct Store {
    open: Vec<String>,
}

#[clifacet::planned]
impl PlannedWith<Store> for Done {
    type Input = DoneInput;
    type Output = String;

    fn plan<'a>(&'a self, input: DoneInput, store: &'a Store) -> Result<Plan<'a, String>, Failure> {
        if !store.open.contains(&input.task) {
            return Err(Failure::validation(format!("there is no open task named {}", input.task)));
        }
        let step = format!("mark {} done", input.task);
        let task = input.task;
        Ok(Plan::new(move || Ok(format!("{task} is done"))).step(step))
    }
}

let store = Store { open: vec![String::from("CLI-47")] };
let app = App::<Done>::new().context(move || Ok::<_, std::io::Error>(Store {
    open: store.open.clone(),
}));
let (mut out, mut err) = (Vec::new(), Vec::new());
let code = app.run_with(
    ["done", "--task", "CLI-47", "--dry-run"],
    clifacet::policy::Capabilities::headless(),
    || Box::new(Scripted::new([])),
    &mut out,
    &mut err,
);
assert_eq!((code, out.as_slice()), (0, b"mark CLI-47 done\n".as_slice()), "{err:?}");
```

</Accordion>

<Accordion title="Settings from a file, under the flags">

### Settings from a file, under the flags

A flag is one place a value comes from. The other three, in the order they win, are the
environment, a settings file, and the built-in default. `App::settings` supplies the third,
and nothing else changes: the file's values become `clap` defaults, so the order is `clap`'s
own and each value is parsed by the same parser as the flag.

```rust ignore
use clifacet::settings::toml::Toml;

App::<Cli>::new()
    .settings("my-app", Toml)
    .run();
```
