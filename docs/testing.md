# Testing the command core

The suite has four kinds of test, because they answer different questions. A case
table is not a scenario, and neither is a property; decision-6 assigns each one a
job, and this page records what is actually installed and how to run it.

| Question | Tool | Command | Lives in |
| --- | --- | --- | --- |
| Which value does each layer produce, for this argv? | `rstest` cases | `pixi run test` | `crates/clifacet-example/tests/validation_matrix.rs` |
| Does the user-facing promise hold, end to end? | `rstest-bdd` | `pixi run test` | `crates/clifacet-example/tests/features/`, `*_bdd.rs` |
| Does it hold for inputs no table would enumerate? | `proptest` | `pixi run test` | `crates/clifacet-example/tests/properties.rs` |
| Does a mistake in the derive read clearly? | `trybuild` | `pixi run test` | `crates/clifacet/tests/ui/`, `crates/clifacet-macros/tests/ui/` |

`pixi run test-local` runs all of them plus fmt, clippy, alint, the documentation
checks, the Python checks and `cargo deny`; it is the gate before a feature is claimed.
The documentation is part of the suite too: every compiled snippet in the guides is a
test in `crates/clifacet-example/tests/documented_snippets.rs`, generated by
`scripts/check_docs.py`.

A fifth question sits across all three modes — does the mode that collected the input
change anything else? — and `clifacet::harness` is the published answer: it measures a
run, records what the command received, and compares runs from different frontends.
`crates/clifacet-example/tests/harness_parity.rs` drives the reference application
through flags, a scripted prompt and the headless form, and
`crates/clifacet/tests/harness.rs` covers the harness itself. See
[`command-core.md`](command-core.md#cross-mode-parity-as-a-published-api).

## What each layer asserts

`validation_matrix.rs` keeps the layers apart, because they are separate promises:

- **draft** — what `clap` collected, before any application rule runs. A later
  frontend fills in this state, so its shape is a contract, and out-of-range values
  are allowed to appear here (`--repeat 9` parses).
- **input** — the validated value. Normalization (trimming, the `world` default,
  the range check) happens on the way in, and every value is runnable.
- **validation** — what is refused, with the exact message the user reads.

Stream and exit-code behavior stays in
`crates/clifacet-example/tests/example_command.rs`, which drives the application
through buffers; the matrix does not repeat it.

## Properties, and what they are allowed to claim

`properties.rs` states four invariants:

1. a canonical input survives a round trip through argv — no field is lost in the
   bridge, and the flags render the input faithfully;
2. the same argv never produces two different answers;
3. every argv lands on one of the three documented exit codes, without panicking,
   and a run explains itself on exactly one stream;
4. an accepted name is trimmed and non-blank; a refused one was blank to begin with.

Point 1 is deliberately stated over *canonical* input. Validation normalizes, so
`--name " ada "` does not round trip unchanged — claiming it would be a false
invariant, and point 4 covers the normalization instead.

Point 3 caught a real mistake while it was being written: the first draft asserted
that every run writes to the data stream, which a usage error does not. The
invariant was corrected, not the assertion weakened: failure must explain itself on
the diagnostic stream, and the two streams never carry output at the same time.

Interactive flows are driven through `clifacet_example::main_with`: capabilities are stated
and the frontend is scripted (`clifacet::prompt::Scripted`), so no test can reach a
real terminal. A test that prompts without a script fails with an exhausted-script
error instead of waiting for input.

Failing seeds are written to `crates/clifacet-example/tests/proptest-regressions/` and are
committed, so a failure found on one machine re-runs on every other.

## Compatibility, and the limits of what is proven

- The pairing above compiles and passes together in the pinned environment; the
  scenario bindings, the case tables and the properties all run in one `nextest`
  invocation.
- The workspace MSRV is 1.88, and CI proves the *library* at that version across
  every supported feature combination — the same rows `check-features` checks on
  stable, because both read `scripts/check_features.py` rather than keeping two
  lists. The MSRV job runs `cargo check`, which does not build dev-dependencies, so
  the test-only crates above are covered by their declared `rust-version` floors (all
  at or below 1.88) rather than by a 1.88 build. Stating the difference is cheaper
  than discovering it later.
- The suite runs on Linux, macOS and Windows with the stable compiler, headless: each
  frontend test drives its own buffers and keystroke scripts, so no scenario needs a
  terminal and none is skipped for lack of one. What that proves is that the code
  compiles and behaves the same on the three platforms — not that the full-screen
  interface renders well in every terminal.
- Which combinations and platforms count as supported is stated once, in
  [development.md](development.md#supported-platforms-and-feature-combinations).
- Coverage is enforced on source files only, counted by `scripts/check_coverage.py`
  at a 90% line target. The derive's own unit tests are selected by
  `kind(proc-macro)` in the `test-src` task; without that selector `nextest` would
  classify them out of `kind(lib)` and skip them.
- `rstest-bdd` currently pulls the unmaintained `basic-toml` through `gherkin`,
  which is why `.cargo/audit.toml` carries a dated exception (decision-11). CLI-19
  owns revisiting it.
